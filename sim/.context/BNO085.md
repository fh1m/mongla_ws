# BNO085 in simulation — the heading source the vehicle actually flies

`yaw_source` has four options and the sim supported two: `mavlink_ahrs` and
`sim_dvl`. The two it did not are the ones that fly — `bno085` and
`bno085_dvl`. So the entire heading loop (`HeadingLock`, `motion_yaw`, every
`turn`, every `lock_heading`) could only be tuned against a sensor the vehicle
does not use, and `BNO085Source` itself — its calibration handshake, its
staleness window, its sign convention — had never executed outside the pool.

`duburi_sim_bridge/bno085_sim.py` closes that. It starts with the rest of the
sim (`bno085:=false` to disable), and `duburi_sim stack` already points the
manager at it.

```bash
ros2 run duburi_sim_bringup duburi_sim sim
#   [BNO-SIM] virtual BNO085 on /dev/pts/11 (symlink /tmp/duburi-$USER/bno085)
#             @ 50 Hz, drift 0.50 deg/min (this run: +0.839 deg/min)

ros2 launch duburi_sim_bringup stack.launch.py yaw_source:=bno085
#   [SENS ] BNO085 calibrated  pixhawk=90.00°  bno_raw=36.79°  offset=+53.21°
```

`bno085_port:=auto` restores USB VID/PID scanning.

## `bno085_sim_dvl` — the pool configuration, in sim

The pool runs **`bno085_dvl`**: BNO for heading, Nucleus DVL for position. In
sim the Nucleus is unreachable, so that source comes up heading-only and every
`*_dist` verb is dead — the configuration the vehicle actually flies had no sim
equivalent at all, even with the virtual board.

`bno085_sim_dvl` is the same composite with the Gazebo DVL in the Nucleus's
place. Measured, single manager, one arm:

```
turn --target 180        -> 177.786  (err 2.214)
move_forward_dist 1.0    -> completed 1.02m of 1.00m (DVL)
move_lateral_dist 0.8    -> completed 0.82m of 0.80m (DVL)
```

```bash
ros2 run duburi_sim_bringup duburi_sim stack --no-vision \
    yaw_source:=bno085_sim_dvl
```

`duburi_sim stack` now passes any `key:=value` through, which matters more than
it sounds: **launching `stack.launch.py` by hand skips the kill of prior
stacks**, and two managers on `udpin:14550` fight in a way that looks exactly
like a broken sensor. Five accumulated managers made three separate
measurements here read as failures — `move_forward_dist` reporting FAIL while
the server logged `DONE (completed 1.02m of 1.00m)` — and the control arm on
`sim_dvl` failed identically, which is what proved it was the harness rather
than the new source. Count them with
`ros2 node list | grep -c duburi_manager`; the answer must be 1.

## The real driver connects to it, unmodified

The firmware contract is a line of JSON over USB CDC at 115200
(`src/duburi_sensors/firmware/esp32c3_bno085.md`), so a PTY presents a device
node that `BNO085Source` opens with its own `Serial()` setup, its own
`readline()`, its own parser and its own calibration. Nothing in
`duburi_sensors` is sim-aware.

That matters more here than for the payload: a `sim_bno085` yaw *source* would
be new code testing itself, and the Pixhawk calibration handshake — the part
most likely to break — would never run at all.

**One flight-code change was needed**, and it is a real robustness fix rather
than a sim accommodation. `BNO085Source` set `dtr = True` after opening the
port; on a device with no modem control lines that raises
`OSError: [Errno 25] Inappropriate ioctl for device`, and unhandled it took the
whole sensors node down before a single frame was read. It is now caught and
logged. On real hardware the ioctl succeeds and the behaviour is unchanged.

## Two conventions, both silent if wrong

**The board emits +CCW, sensor-frame.** `_reader_loop` negates the raw value
once at ingestion because the firmware is ENU-native while the rest of the
stack is compass/NED. Emitting compass yaw from the board would leave the sign
inverted with no error — a heading lock that drives away from its target.

**The board emits a BOOT-RELATIVE frame.** The real BNO runs with the
magnetometer disabled, so its zero is wherever the chip sat at power-on; the
Jetson captures `pixhawk_yaw - bno_raw` once and adds it forever after.
Publishing true heading here would make that handshake a no-op. The default
`boot_offset_deg` is 37°, deliberately not 0, so a stack that skipped
calibration reads visibly wrong rather than accidentally right.

## Measured against ground truth

`/duburi/state` under `yaw_source:=bno085` is the board's output after the PTY,
the real driver, the negation and the locked offset. Gazebo's odometry is
truth. Through four commanded turns:

| commanded | ground truth | BNO (stack) | error |
|---|---|---|---|
| 90 | 97.99 | 98.02 | 0.03 |
| 180 | 189.81 | 189.93 | 0.12 |
| 270 | 268.90 | 268.90 | 0.00 |
| 45 | 54.57 | 54.74 | 0.16 |

Worst error 0.16°. And `turn` **terminates** on this path, which it cannot do
with real hardware on a desk — the startup HINT about that ("the BNO chip does
NOT move when ArduSub yaws in Gazebo") no longer applies in sim, because this
board reads Gazebo.

> A trap worth recording: the first version of that comparison showed a
> constant 90.1° error and looked like a broken sensor. The *test* was wrong —
> ENU yaw 0 points along +x, which is EAST, so `compass = 90 - enu`, not
> `-enu`. The consistency across all four rows was the clue: a real fault
> would vary.

## Drift is from the datasheet

BNO08X datasheet rev 1.17, Figure 6-14:

```
Gaming Rotation Vector Nominal ... Dynamic Heading Drift   0.5°/min
Gyroscope Nominal ................ Dynamic Accuracy        3.1°/s
```

The Gaming Rotation Vector row is the applicable one. Our firmware runs
`SH2_GYRO_INTEGRATED_RV` with the magnetometer disabled, and datasheet §2.2.6
says the gyro rotation vector is "configured via FRS record to be based on
either the rotation vector (using the magnetometer) or the game rotation
vector (ignoring the magnetometer)" — ours is the latter. The datasheet gives
no separate drift figure for the gyro-integrated variant.

Drift is modelled as a **fixed per-run bias**, so heading error grows linearly.
That is the datasheet's own explanation of the figure: "removal of gyroscope
ZRO is critical to reduce heading drift" (§3.3), and zero-rate offset is
essentially constant across a power-up. Ten minutes gives about 5°, which is
why a long mission wants a re-zero.

**It was a random walk first, and measurement rejected it twice over**: a walk
grows as √t rather than t, and its coefficient had been divided by 60 as
though it were a rate when a walk's scales as √60 — together making the drift
**7.7× too weak** at one minute. A sim that holds heading better than the
vehicle is worse than no model, because it hides the problem the operator has
to plan around.

Per-sample noise is the gyro rate accuracy over one frame: 3.1°/s ÷ 50 Hz =
0.062°, which averages out and is small next to the 2° yaw deadband.

## Fidelity limits

The **protocol, driver and calibration path are exact** — that is flight code.
The **noise model is weaker grounding than the T200 curve**, which came from
published measurements: the datasheet gives a single drift figure and no
Allan-variance curve, so the bias distribution here is the datasheet magnitude
applied as a normal draw, not a fitted model. Vibration, temperature drift and
the `wasReset()` recovery path are not modelled.

`dropout_s` stops the stream so the source's staleness path can be exercised:

```bash
ros2 param set /bno085_sim dropout_s 5.0
```
