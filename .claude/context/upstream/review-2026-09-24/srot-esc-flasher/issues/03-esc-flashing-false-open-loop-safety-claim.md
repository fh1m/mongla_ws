# ESC_FLASHING.md claims the Pico drives an ESC without telemetry "open-loop, feedforward only, no integrator"; the Pico has no such fallback

Part of the 2026-09-24 ecosystem review, round 2 (see ../README.md).

## Summary
The safety note at the top of `docs/ESC_FLASHING.md` says that until an ESC reports telemetry, the Pico automatically drives that motor open-loop (feedforward only, no integrator), "so it can never run away", and that arming and testing with stock ESCs is therefore safe. The Pico firmware has no such per-ESC fallback:
- With `RPM_LOOP=0` (the board default since `PARAM_DEFAULTS_VER` 4) there is no RPM loop at all. The Pico sends the ESP32's raw DShot values. The note describes a mode that is not running.
- With `RPM_LOOP=1`, a channel with no telemetry is still driven by **feedforward + P + the held integrator**. Only the integrator *update* is gated on telemetry. Because the Pico zeroes the filtered RPM of an absent ESC, the P term sees the full target as error and adds `kp·target/RPM_MAX` on top of the feedforward.

The practical risk is bounded, since the level is clamped to ±1 and slew-limited. But the note makes a specific safety claim ("feedforward only, no integrator … can never run away") that the code does not implement, in the document people read before powering thrusters. Issue #2 covers the `RPM_LOOP` default on line 121 of the same file. This is the separate claim on lines 15-17. If #2 already covers this paragraph, post this as a comment there instead.

## Failure scenario
An operator bench-tests a mix of Bluejay and stock ESCs with `RPM_LOOP=1`, relying on the note. The stock ESCs are driven with feedforward plus a P term on a zero measurement, plus whatever integrator the channel held from earlier telemetry. That is more than the "feedforward only" level they expected. It is still bounded, but the operator's mental model of what the board does with an unknown ESC is wrong, and the doc told them it was a safety property.

## Suggested fix
Replace the note with what the code does:
> With `RPM_LOOP=0` (the default) the Pico sends the ESP32's raw DShot values, with or without telemetry. With `RPM_LOOP=1`, a channel without telemetry keeps feedforward + P (on a zero measurement) and its held integrator. There is no automatic open-loop fallback.

Or, if the fallback is wanted, open a PR on srot-control-board so that `!has_tlm` really means feedforward only (skip `kp·err` and `s_integ`), and keep the note. Either way, the doc and the code must say the same thing.

## How to verify (bench)
With `RPM_LOOP=1`, props off, one ESC with its telemetry wire disconnected: command a target and read the Pico's USB debug `out=` value for that channel. Compare it with `RPM_FF_A × target` (feedforward only). Today it is higher by about `kp·target/RPM_MAX`.
