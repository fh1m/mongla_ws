# LoRa bridge forwards the board's WTEMP "no data" sentinel (INT8_MIN) as a real reading: Bondor shows -128.0 °C, and depth over LoRa cannot express "absent" at all

Part of the 2026-09-24 ecosystem review (tracking issue in fh1m/mongla_ws to follow).

## Summary
The control board encodes "no water temperature" in the LoRa frame as `wtemp_c = INT8_MIN (-128)`. The ground-station bridge converts that byte straight to `NAMED_VALUE_FLOAT "WTEMP" = -128.0`. Bondor's Water tile checks only for `undefined`, so over LoRa it shows **-128.0 °C** whenever the barometer is unhealthy. That breaks the house rule *absence renders "—", never a number*, and it happens on exactly the link where the operator cannot cross-check against USB.

Depth has the same shape, but worse: the frame has no validity bit for depth, and the board keeps the last good `depth_m` when the baro goes unhealthy. So LoRa depth shows a **frozen, plausible number** after the board has withdrawn depth.

## Evidence (at `1adc14c`)
Board side, `srot-control-board/src/tasks/task_lora_sd.cpp:86-96` (at `f1d3ba9`):
```cpp
// INT8_MIN (-128) = "no data". ...
t.wtemp_c = (fresh && wt > -127.0f && wt < 127.0f) ? (int8_t)wt : (int8_t)INT8_MIN;
```
Bridge, `src/groundstation/main.cpp:386`:
```cpp
named("WTEMP", (float)t.wtemp_c, now);
```
Bondor, `bondor/src/renderer/src/views/DiveView.tsx:160`:
```tsx
value={t.named['WTEMP'] !== undefined ? t.named['WTEMP'].toFixed(1) : '—'}
```
Depth: `task_lora_sd.cpp:80` `t.depth_cm = (int16_t)(x.depth_m * 100.0f);` has no validity gate. `task_sensor_read.cpp:257-268` updates `depth_m` only `if (baro_new)` and sets `baro_valid` separately. The bridge `main.cpp:344` always emits `VFR_HUD.alt = -(depth_cm/100)`. `shared/lora_telem_proto.h:27-30` defines flag bits 0-3, and bits 4-7 are free.

## Failure scenario
The Bar30 connector is flaky (BENCH_FINDINGS 2026-08-02 §1). Rev 5's jitter gate marks the baro unhealthy. Over USB, Bondor correctly shows Water "—". Over LoRa it shows **-128.0 °C**, and Depth shows the last good value, frozen, with nothing on screen to say it is stale. An operator watching LoRa during a surface test reads a steady depth while the board has refused DEPTH_HOLD.

## Suggested fix
1. **Bridge (no wire change):** `if (t.wtemp_c != INT8_MIN) named("WTEMP", ...)`. Stay silent, so the tile falls to "—". (Once #2 lands, the tile will also age out.)
2. **Depth (wire change, so coordinate per AGENTS.md invariant 1):** add `LT_FLAG_DEPTH_OK (1 << 4)` on the board, set from the same `fresh` predicate used for wtemp. In the bridge, skip `VFR_HUD` (or send `alt = NaN`) when the bit is clear. The struct size does not change, so an un-reflashed pair degrades to "no depth" rather than going silent. This needs a PR in `srot-control-board` for the board half.

## How to verify
- Bench over LoRa: unplug the Bar30 (or force `baro_valid = false`). Before the fix, Water reads -128.0. After, "—".
- For depth: with the flag in place, unplug the Bar30 and confirm the Depth tile goes to "—" over LoRa within 1 s (after PR #4's absence rendering lands).

## Severity: Medium
A manufactured reading on the operator's primary remote link. -128 °C is obviously wrong, but a frozen depth is not.
