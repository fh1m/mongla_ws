# "Save to flash" stops seeing the board's answer after 200 STATUSTEXTs or 50 ACKs: a SAVE FAILED shows as "accepted" or "no reply", and the blackbox stops logging status lines

Part of the 2026-09-24 ecosystem review (tracking issue in fh1m/mongla_ws to follow).

## Summary
`statusText` is capped at 200 entries and `acks` at 50 by `slice(-N)`. Once either array is full, **its length stops growing**. `saveParams()` and the blackbox recorder both find "new" entries by remembering `array.length` and later reading `array.slice(thatLength)`. At the cap that slice is **always empty**, so neither sees anything that arrives afterwards.

## Evidence (at `1adc14c`)
`bondor/src/renderer/src/store/telemetry.ts:309`: capped at 200:
```ts
set({ statusText: [...get().statusText.slice(-199), { ts: m.ts, severity: Number(f.severity), text }] })
```
`:315`: capped at 50:
```ts
acks: [...get().acks.slice(-49), { ts: m.ts, command: ..., result: ..., progress: ... }]
```
`:484-508` (`saveParams`):
```ts
const ackFrom = get().acks.length          // 50 once capped
const textFrom = get().statusText.length   // 200 once capped
...
const ack = get().acks.slice(ackFrom).find(...)            // always []
for (const line of get().statusText.slice(textFrom)) { ... } // always []
```
`:389` and `:406-409` (recorder): `recStatusSeen = get().statusText.length`, then `for (let i = recStatusSeen; i < s.statusText.length; i++)`. At the cap this loop never runs.

## Failure scenario
- **The worst case: the tune is lost, and the UI says the save was probably fine.** Late in a pool session the board has sent more than 200 STATUSTEXTs (arming checks, "depth refused" reasons, failsafe messages, autotune progress), but fewer than 50 COMMAND_ACKs. The operator presses Save. The ACCEPTED ack is seen, but the board's `SAVE FAILED - params NOT written` line is not, so the outcome is `assumed` ("accepted, but this firmware does not confirm writes", shown as blue *info*). The tune is gone at the next boot. `ParamsView.doApply` (`ParamsView.tsx:112`) calls `saveParams()` after every Import, so this also affects the Export → flash → Import restore flow that AGENTS.md prescribes.
- After ~50 ACKs (a few SROT_MOVEs is enough, since each streams IN_PROGRESS acks), every save reports **`no-reply`** even when it succeeded. That trains operators to ignore the result.
- The blackbox `events.csv` silently stops including status lines partway through a session.

## Suggested fix
Stop using the array length as a cursor. Two options:
- Give each entry a monotonically increasing `seq` from a module counter, remember `const since = nextSeq` before sending, and filter with `e.seq >= since`; or
- Filter by timestamp: record `const t0 = Date.now()` before sending and use `.filter((a) => a.ts >= t0)`. The `ts` field is already on both `StatusLine` and `AckLine`.

Apply the same change to the recorder (`recStatusSeen`), and search the codebase for any other `slice(prevLength)` cursors.

## How to verify
- Unit: push 250 STATUSTEXTs into `ingest`, call `saveParams()`, then inject an ACCEPTED ack and a `SAVE FAILED` STATUSTEXT. Before the fix the result is `assumed`; after the fix it is `failed`.
- Same with 60 acks pre-filled and a "Params saved to flash" line. Before: `no-reply` or `assumed`. After: `saved`.
- Injection check: restore the `.length` cursor and watch the test fail.

## Severity: Medium
It silently defeats the safeguard that `saveParams` was written to provide (the comment at `:473-482` explains why the ACK alone is not trusted). The result is a lost tune, not a vehicle hazard, and the reload hint in the "assumed" text softens it.
