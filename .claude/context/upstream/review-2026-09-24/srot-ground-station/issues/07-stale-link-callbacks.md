# A closed link's late 'close'/'error' event can stop the NEW link's GCS heartbeat (callbacks are not bound to the link instance), and a USB serial link never reconnects

Part of the 2026-09-24 ecosystem review (tracking issue in fh1m/mongla_ws to follow).

## Summary
`MavlinkConnection.connect()` gives each link a callback object whose `onStatus` writes to the **connection-wide** status and starts or stops the **connection-wide** heartbeat. When the operator reconnects, `connect()` calls `disconnect()`, which calls `link.close()`. For `SerialLink`, `port.close()` completes asynchronously and then emits `'close'`, which calls the **old** link's callback: `setStatus({connected:false})` + `stopHeartbeat()`. If that event lands *after* the new link has reported `connected: true` (switching serial → UDP, USB → LoRa-bridge COM port, or a slow close on Windows), the new, healthy link is marked disconnected and **its heartbeat is stopped**. The board then surfaces after `GCS_FAILSAFE_MS`, and every command button is disabled.

Separately, the serial link has **no reconnect**. A USB re-enumeration (brown-out, a cable bump, the board resetting) emits `'close'`, the heartbeat stops, and the operator has to notice and reconnect by hand. `UdpLink` gained auto-reopen in `a4c2b36`; `SerialLink` did not.

*Not reproduced on hardware.* This is an ordering race read from the code. The heartbeat-stop consequence follows directly if the ordering occurs.

## Evidence (at `1adc14c`)
`bondor/src/main/mavlink/connection.ts:97-104`: the callback is not tied to the link that owns it:
```ts
const cb = {
  onData: (buf: Buffer) => this.splitter?.write(buf),
  onStatus: (s: LinkStatus) => {
    this.setStatus({ ...s, kind: opts.kind })
    if (s.connected) this.startHeartbeat()
    else this.stopHeartbeat()
  }
}
```
`connection.ts:122-131`: `disconnect()` closes the link and nulls it, but nothing stops the old link's callbacks from firing later.
`bondor/src/main/mavlink/serialLink.ts:33-34`:
```ts
this.port.on('error', (err) => cb.onStatus({ connected: false, error: err.message }))
this.port.on('close', () => cb.onStatus({ connected: false }))
```
`onData` has the same shape: late bytes from the old port are written into the **new** splitter (`this.splitter` has already been replaced), which can interleave half-frames. The CRC check catches most of that, but it is still unintended.

## Failure scenario
The operator is connected to the board over USB and switches to the LoRa bridge's COM port to test range. The new port opens, `connected: true`, and the heartbeat starts. Then the old port's delayed `'close'` fires: status goes to `connected:false` and the heartbeat stops. Bondor shows "Offline/Connect" with telemetry still arriving, and the board (if the bridge's `s_last_usb_ms` lapses because Bondor stops writing) sees GCS loss and surfaces.

## Suggested fix
- Bind callbacks to the link instance with a generation counter:
  ```ts
  const gen = ++this.gen
  const cb = { onData: (b) => { if (gen === this.gen) this.splitter?.write(b) },
               onStatus: (s) => { if (gen !== this.gen) return; ... } }
  ```
  and bump `this.gen` in `disconnect()`.
- Add a reopen-with-backoff to `SerialLink`, mirroring `UdpLink.scheduleReopen` (re-list ports and match by `path`, or by serialNumber/VID:PID after re-enumeration). Keep reporting `connected:false` while reopening, so the heartbeat really stops in the meantime.

## How to verify
- Unit: construct `MavlinkConnection` with a fake link whose `close()` defers `onStatus({connected:false})` by `setTimeout(…, 50)`. Call `connect(A)` then `connect(B)` (B reports connected at once). Before the fix, after 50 ms `status.connected === false` and `hbTimer === null`. After the fix, B stays connected.
- Bench: connected over USB, unplug and replug the board. Before: it stays "Offline". After: it reconnects within the backoff window.

## Severity: Medium
Stopping the heartbeat on a live link surfaces the vehicle and disables the operator's controls, but the trigger needs a reconnect while connected, and the ordering has not been observed on hardware.
