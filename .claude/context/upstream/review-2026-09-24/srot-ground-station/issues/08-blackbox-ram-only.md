# Blackbox recording lives only in renderer RAM: it is lost on reload, crash or quit, has no autosave, and uses wall-clock time for `t`

Part of the 2026-09-24 ecosystem review (tracking issue in fh1m/mongla_ws to follow).

## Summary
`373741f` moved the recorder to module scope so it survives tab changes. It still does not survive a **renderer reload, crash or app quit**: rows exist only in `recRows`/`recEvents` in renderer memory, and are written to disk only when the operator clicks Export on the Analyze tab. The recordings most worth keeping (the one where something went wrong and the operator reloaded, or Bondor hung) are exactly the ones that are lost. There is also no warning when quitting with an unexported recording.

The sample clock is `Date.now()`, which is wall-clock and non-monotonic: an NTP step or a laptop resuming from sleep mid-recording makes `t` jump or go backwards, which corrupts time alignment against duburi_ws bags.

## Evidence (at `1adc14c`)
`bondor/src/renderer/src/store/telemetry.ts:84-92`:
```ts
let recRows: Record<string, number>[] = []
let recEvents: BlackboxEvent[] = []
...
const recElapsed = (): number => (Date.now() - recT0) / 1000
```
`:391-412`: samples are pushed into the array at 20 Hz, and nothing is flushed. `AnalyzeView.tsx` `exportCsv` is the only writer (via a Blob download). No `beforeunload` guard exists (`grep -rn beforeunload bondor/src` returns nothing).
Memory: every row is an object with ~15 fixed keys plus one key per NAMED_VALUE_FLOAT seen (dozens). At 20 Hz a 1 h session is 72 k objects. That is not fatal, but it grows without bound, and `recordingCsv()` builds the whole CSV as one string.

## Failure scenario
The vehicle does something unexpected during a pool run. The operator, trying to get the UI back, presses Ctrl+R (or Bondor's renderer hangs and is killed). The flight recording, the only host-side record with Bondor's commands interleaved, is gone.

## Suggested fix
- Stream to disk from **main**. Add an IPC `recAppend(lines)`, and have the renderer batch every ~1 s, or better, have main write every decoded message itself so the recorder does not depend on the renderer at all. Write to `userData/recordings/<iso>.csv` with an `fsync` every few seconds, so a crash loses ≤ a few seconds.
- Use `performance.now()` (monotonic) for `t`, and write the wall-clock start once in a header line (`# t0_epoch_ms=...`).
- Add a `beforeunload` / `app.on('before-quit')` prompt when a recording is running or unexported.
- Optional: record per-signal **age** (or leave the cell blank when a value is stale) so the CSV does not repeat held values. This depends on #2.

## How to verify
- Start recording, wait 30 s, press Ctrl+R. Before: the recording is gone. After: a file with ~600 rows exists in `userData/recordings/`.
- Start recording, then change the system clock by -1 h. Before: `t` jumps negative. After: `t` stays monotonic.

## Severity: Medium
Data integrity of the one host-side flight record. It is not a vehicle hazard, but it destroys evidence at the moment it is most needed.
