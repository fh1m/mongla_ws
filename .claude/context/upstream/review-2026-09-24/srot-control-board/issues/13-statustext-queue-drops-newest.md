# The cross-core STATUSTEXT queue has 4 slots and drops the newest, so a failsafe burst can lose the line that says why

Part of the 2026-09-24 ecosystem review (tracking issue in fh1m/mongla_ws, link to follow).

## Summary
Core 1 (the control loop, autotune, calibration and the sensor task) reports its decisions through `queueStatusText()`. The queue holds 4 entries. When it is full, the **new** message is dropped silently, whatever its severity. A failsafe edge usually comes together with several other messages, so the CRITICAL "why" can be the one that is lost.

## Evidence
At commit `f1d3ba9`, `src/comms/mav_stream.cpp:352-369`:
```cpp
static const uint8_t QCAP = 4;
static char    s_q[QCAP][64];
...
void queueStatusText(uint8_t severity, const char* text) {
    if (!text) return;
    portENTER_CRITICAL(&s_qmux);
    if (s_qcount < QCAP) {
        ...
        s_qcount++;
    }                                   // else: dropped, no counter, no trace
    portEXIT_CRITICAL(&s_qmux);
}
```
The queue is drained by `flushQueuedStatusText()` from the 100 Hz MAVLink task. Any stall of core 0 lets messages pile up: a flash write (see the NVS issue), a blocking `txReliable` on a full UART, or a param stream.

## Failure scenario
1. At depth the board has already queued "Depth auto-zeroed", a baro-jitter warning and an autotune line, and core 0 is in a 40 ms `PARAM_SET` flash write.
2. The leak failsafe latches and queues "Failsafe: surfacing (leak)" at CRITICAL severity (`task_control_loop.cpp:708-709`). The queue is full, so the message is dropped.
3. The failsafe announcement is edge-latched (`s_fs_last`), so it is never sent again. The operator and the companion see the vehicle switch to `SURFACE` with no reason given, and the host cannot tell a leak from a GCS-loss failsafe.

## Suggested fix
- Raise `QCAP` to 16. That costs about 1 KB, which the RAM budget easily allows (24 % used).
- When full, **evict the lowest-severity entry** (highest numeric `MAV_SEVERITY`) if the incoming message is more severe. Otherwise drop the incoming one.
- Count drops, and after the next successful flush emit `STATUSTEXT "N status messages dropped"`.
- Trim the slot to 50 chars. `STATUSTEXT.text` is `char[50]`, so the 64-byte slots waste 14 bytes each.

## How to verify
- **Unit or bench test:** hold the MAVLink task off (for example with a debug param that makes it sleep 200 ms), queue 10 INFO messages and 1 CRITICAL message from core 1, then release. The CRITICAL message must arrive, followed by a "dropped" notice.
- **Injection test:** restore drop-newest and confirm the CRITICAL message is lost.

## Severity: Medium
The board's safety decisions are its most important messages, and this queue can lose them.
