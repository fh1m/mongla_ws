# A PARAM download blacks out VFR_HUD (depth), SYS_STATUS (baro and leak health), LEAK and BATTERY for 10–15 s, against the scheduler's own rule

Part of the 2026-09-24 ecosystem review (tracking issue in fh1m/mongla_ws, link to follow).

## Summary
While any station is downloading the parameter list, the stream scheduler sends only HEARTBEAT, ESC_STATUS and ATTITUDE. The comment directly above that branch states the rule: "Anything a MISSION depends on belongs above this guard." The companion's depth feed (`VFR_HUD`), baro and leak health (`SYS_STATUS`), `NAMED_VALUE_FLOAT LEAK`, `SCALED_PRESSURE2` and `BATTERY_STATUS` are all below the guard. Any `PARAM_REQUEST_LIST`, for example from Bondor opening its Setup tab, blinds an autonomous run to depth and leak for the length of the download.

## Evidence
At commit `f1d3ba9`, `src/comms/mav_stream.cpp:797-807`:
```cpp
    // ATTITUDE is exempt for the same class of reason: it is the companion's control-loop
    // input, and a 10-15 s blackout mid-mission is a 10-15 s hole in every host-side loop
    // that closes on attitude. An operator opening Bondor's Setup tab must not be able to
    // blind an autonomous run. Anything a MISSION depends on belongs above this guard;
    // anything only a human reads belongs below it.
    if (mav_commands::paramDownloadActive()) {
        if (now - t_hb >= iv_hb) { t_hb = now; sendHeartbeat(s); }
        if (iv_esc && now - t_esc >= iv_esc) { t_esc = now; sendEscStatus(s, now); }
        if (iv_att && now - t_att >= iv_att) { t_att = now; sendAttitude(s, now); }
        return;
    }
```
Below the guard (`:809-831`) are `sendSysStatus`, `sendScaledPressure`, `sendVfrHud`, `sendBattery` and the NVF block with `LEAK`. `PARAM_REQUEST_LIST` is accepted from any sender (`mav_commands.cpp:759-766`).

## Failure scenario
1. The vehicle is at 1.5 m running an autonomous mission from the companion.
2. The pool-side operator opens Bondor's Setup tab, which sends `PARAM_REQUEST_LIST` over LoRa or USB.
3. For 10–15 s the companion gets no `VFR_HUD`, so the depth topic becomes `NaN`. It gets no `SYS_STATUS`, so baro and leak health are unknown, and no `LEAK`. Depth-gated host logic refuses verbs or aborts. Worse, any host consumer that holds its last value (see the VFR_HUD issue) flies blind.
4. A leak that starts during the window is not reported to the companion until the download ends. The board-side failsafe still acts, so the vehicle is safe, but the host cannot know why it is surfacing.

## Suggested fix
Move the mission-critical, low-bandwidth messages above the guard, following the file's own rule:
```cpp
    if (mav_commands::paramDownloadActive()) {
        heartbeat; esc; attitude;
        if (iv_sys && now - t_sys >= iv_sys) { t_sys = now; sendSysStatus(s); }   // health + leak
        if (iv_hud && now - t_hud >= iv_hud) { t_hud = now; sendVfrHud(s); }       // depth
        return;
    }
```
Each is about 40–50 B. At 4–5 Hz that adds about 0.4 kB/s, roughly 3–4 % of the 115200 link. Optionally, stretch their interval ×2 during a download instead of dropping them. Better still, limit downloads to disarmed, or throttle them while armed.

## How to verify
- **Bench:** with the board armed (props off), start a param download from QGC or Bondor. In `connect --watch`, `VFR_HUD` and `SYS_STATUS` must keep arriving, at no less than half their normal rate, for the whole download.
- Measure the download duration before and after the change to confirm the cost is small.
- **Injection test:** move `sendVfrHud` back below the guard and confirm a host-side test ("depth never absent for >1 s during a param download") fails.

## Severity: Medium
A routine operator action blinds the companion to depth and leak for 10–15 s mid-mission. The board's own failsafes are unaffected.
