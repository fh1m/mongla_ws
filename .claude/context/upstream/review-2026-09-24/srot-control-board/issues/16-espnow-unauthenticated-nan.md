# ESP-NOW input from the second board is unauthenticated and not NaN-checked: a spoof can trigger a surface, and NaN disables the low-battery failsafe and voltage compensation

Part of the 2026-09-24 ecosystem review (tracking issue in fh1m/mongla_ws, link to follow).

## Summary
`espnow_link::onRecv` accepts any ESP-NOW frame that has the right magic number. It ignores the sender MAC, uses no encryption or sequence number, and never checks that `aux_voltage` is finite. That voltage feeds the thruster-battery failsafe and the mixer's voltage compensation. A NaN (from an ADC or firmware bug on the second board, or a crafted frame) makes the failsafe test permanently false and poisons the compensation filter. A spoofed low voltage held for 3 s surfaces the vehicle.

## Evidence
At commit `f1d3ba9`.

`src/drivers/espnow_link.cpp:23-33`:
```cpp
static void onRecv(const uint8_t* mac, const uint8_t* data, int len) {
    (void)mac;
    if (len < (int)sizeof(FromSecond)) return;
    FromSecond p;
    memcpy(&p, data, sizeof(p));
    if (p.magic != MAGIC) return;
    s_kill = (p.thruster_kill != 0);
    s_aux = p.aux_voltage;
```
`src/tasks/task_lora_sd.cpp:208-209` stores it after multiplying by `PM2_VMULT`, with no `isfinite` check.

`src/tasks/task_control_loop.cpp:664-666`: `NaN > 1.0f` is false, so the failsafe is off while NaN is present.
```cpp
            const float bat_v = in.thr_volts;
            if (in.armed && g_params.fs_bat_enable > 0 &&
                bat_v > 1.0f && bat_v < g_params.fs_bat_voltage) {
```
`src/control/mixer.cpp:78-84`: NaN passes `volts < 1.0f`, and `constrain(NaN, …)` returns NaN.
```cpp
    if (vmax < 1.0f || volts < 1.0f) { s_v_norm = 0.0f; return; }
    ...
    float v = constrain(volts, vmin, vmax) / vmax;
    s_v_norm = (s_v_norm <= 0.0f) ? v : s_v_norm + a * (v - s_v_norm);
```
Once `s_v_norm` is NaN it stays NaN until a stale or zero reading resets it, and `batteryScale()` returns 0, which disables compensation.

## Failure scenario
1. **NaN (hypothetical trigger):** suppose a bug in the second board's ADC averaging, such as a divide by a zero sample count after a brown-out, sends `aux_voltage = NaN`. From then on the low-thruster-battery failsafe cannot trip, voltage compensation is off, and the OLED and LoRa show `nan`. The vehicle runs its pack flat at depth.
2. **Spoof, on deck or bench only:** 2.4 GHz does not propagate through water. Anyone with an ESP32 on the right channel broadcasts `{magic, kill=0, aux_voltage=5.0}` at 4 Hz. After `FS_BAT_HOLD_MS` of 3 s the armed vehicle switches to `SURFACE`. A spoofed `kill=1` currently only changes the display (see the kill-switch issue). It would become a control input once that issue is fixed, so authentication matters before that change.

## Suggested fix
- In `onRecv`, drop the frame when `!isfinite(p.aux_voltage) || p.aux_voltage < 0 || p.aux_voltage > 60`, and count it.
- In `mixer::setBatteryVoltage`, add `if (!isfinite(volts)) { s_v_norm = 0; return; }`, the same defensive pattern as `pid.h`.
- **Pin the peer:** store the second board's MAC in a param (`ESPNOW_PEER`, learned on the first frame while disarmed and persisted), and ignore other MACs. Better still, use ESP-NOW's built-in encryption (`esp_now_set_pmk` / `lmk` with an encrypted peer), which costs nothing at runtime. Add a monotonic sequence number to `FromSecond` to reject replays.

## How to verify
- **Unit test:** `setBatteryVoltage(NAN, 0.002)` followed by `setBatteryVoltage(15.0, 0.002)` gives a finite `batteryScale()`.
- **Bench:** a second ESP32 sends a frame with `aux_voltage=NaN`. It must be rejected and counted, and `PM2` must keep its last good value until it goes stale. A frame from an unpinned MAC must be ignored.
- **Injection test:** remove the `isfinite` check and confirm the unit test fails.

## Severity: Medium
The NaN path silently disables a failsafe. The spoof path needs someone within radio range on the deck.
