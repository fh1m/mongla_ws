# Addendum to "The PID integrator limit is in error·seconds": the exact ArduPilot reference, and the autotune coupling it creates

Part of the 2026-09-24 ecosystem review, round 2 (see ../README.md).

**This is an addendum, not a new defect.** It adds evidence to round-1 draft `03-pid-integrator-limit-units.md` (the I-term is capped at 4 % / 0.4 % / 10 %, and the CoB auto-trim mixes units). If 03 has already been filed, post this as a comment on it instead of opening a new issue.

## Summary
Round 1 said "accumulate in output units, as `AC_PID` does". Round 2 pins that to the line, and confirms that our IMAX defaults are ArduSub's own constants. So the parameter is ArduSub's by name and value but not by meaning. It also points out one more consequence: because the ceiling on the I contribution is `ki·imax`, every autotune result that changes Ki also silently moves the integrator's authority.

## Evidence
**ArduPilot clamps the ki-weighted integrator** (`libraries/AC_PID/AC_PID.cpp:345-346` @ ArduPilot `ee0c343`):
```cpp
            _integrator += ((float)_error * _ki) * i_scale * dt;
            _integrator = constrain_float(_integrator, -_kimax, _kimax);
```
**Our defaults are ArduSub's constants** (`libraries/AC_AttitudeControl/AC_AttitudeControl_Sub.h:15-23` @ `ee0c343`):
```cpp
#define AC_ATC_SUB_RATE_RP_P           0.135f
#define AC_ATC_SUB_RATE_RP_I           0.090f
#define AC_ATC_SUB_RATE_RP_D           0.0036f
#define AC_ATC_SUB_RATE_RP_IMAX        0.444f
...
#define AC_ATC_SUB_RATE_YAW_I          0.018f
#define AC_ATC_SUB_RATE_YAW_IMAX       0.222f
```
**Ours clamps the raw ∫e** (`src/control/pid.h:98`, `:101` @ `f1d3ba9`, quoted in full in draft 03):
```cpp
            _integ = constrain(_integ + err * dt, -_imax, _imax);
        const float out = _kp * err + _ki * _integ + _kd * _deriv;
```
**The autotune coupling** (`src/control/autotune.cpp:44-47`, `:185`, `:214` @ `f1d3ba9`):
```cpp
    { 1.0f, 0.6f, 0.04f },   // rate roll   (def 0.135 / 0.090 / 0.0036)
    ...
    float Ki = (Tu > 0) ? Kp / (0.5f * Tu) : 0.0f;
    ...
        case P_RATE_ROLL:  g_params.rat_rll_p = Kp; g_params.rat_rll_i = Ki; g_params.rat_rll_d = Kd; break;
```
A tune that lands Ki at the 0.6 limit raises the roll I-term ceiling from 0.09·0.444 = 0.040 to 0.6·0.444 = 0.27. That is 6.7× more integral authority, and nobody asked for it. It also makes the loop's windup behaviour depend on the tune.

## Failure scenario (additional to draft 03)
1. On the default gains the hull holds a 1–2° list, because the I-term tops out at 4 %.
2. Autotune runs, Ki rises, and the list goes away. The operator concludes that the *tune* fixed the trim.
3. The operator hand-lowers Ki to calm a noisy axis, and the list comes back: the ceiling has dropped with Ki. Changing a gain changes a limit, and no parameter says so.

## Suggested fix
Unchanged from draft 03: store `_integ` ki-weighted, as `AC_PID.cpp:345-346` does, so IMAX is in output units and means what ArduSub means. In addition:
- After the fix, review autotune's `LIMITS[].ki`. It no longer changes the integrator ceiling, so it only needs to bound the integration *rate*.
- Consider bumping `PARAM_DEFAULTS_VER`, or at least adding a PARAMETERS.md note: stored tunes were made under the old coupling.

## How to verify (bench)
Draft 03's unit test, plus: run it with `ki` = 0.09 and `ki` = 0.6 at the same `imax`. **Today:** the output plateau scales with ki (0.040 vs 0.27). **After:** both plateau at 0.444.
