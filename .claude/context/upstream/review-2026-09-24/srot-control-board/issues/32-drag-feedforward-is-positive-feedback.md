# The angular "drag feedforward" uses the measured rate, so it is positive feedback that cancels damping; an overestimated gain gives negative net damping

Part of the 2026-09-24 ecosystem review, round 2 (see ../README.md).

## Summary
`feedforward::apply()` adds `ATC_DRAG_* · ω·|ω|` to each rate-loop output, with ω the **measured** gyro rate. The intent is to pre-inject the counter-torque for quadratic drag, so that "the rate PID then sees a ~linear plant". But hydrodynamic drag already *opposes* the motion. A torque proportional to the measured rate, in the direction of the motion, is positive velocity feedback: it cancels the vehicle's natural damping. With K equal to the true drag coefficient the axis becomes undamped. With K above it, net damping is **negative**, and the rate loop has to overcome an unstable plant. The cross-coupling terms (`XC_YAW2RLL/PIT · gz`) have the same structure and an unanalysed sign.

Feedforward has to be computed from the **reference** (the desired rate), not from the measurement: τ_ff = (M_RB + M_A)·ω̇_ref + (D_l + D_q·|ω_ref|)·ω_ref. On measured signals it is feedback, and its sign has to be designed.

All defaults are 0 (`config.h:542-546`), so this is **latent**. It will bite the first person who tunes it.

At commit `f1d3ba9`.

```cpp
    //    ω·|ω|), so pre-inject the counter-torque; the rate PID then sees a ~linear
    //    plant and only cleans up disturbances. Uses the measured body rates.
    ...
    if (stabilized) {
        roll  += g_params.atc_drag_rll * gx * fabsf(gx);
        pitch += g_params.atc_drag_pit * gy * fabsf(gy);
        yaw   += g_params.atc_drag_yaw * gz * fabsf(gz);
        roll  += g_params.xc_yaw2rll * gz;
        pitch += g_params.xc_yaw2pit * gz;
    }
```
`include/config.h:542-546`: `DEF_ATC_DRAG_RLL/PIT/YAW 0.0f`, `DEF_XC_YAW2RLL/PIT 0.0f`.

The linear model: yaw dynamics I·ṙ = τ_cmd − D·r|r|, with τ_cmd = τ_pid + K·r|r|, gives I·ṙ = τ_pid − (D − K)·r|r|. The effective damping is D − K. It is 0 at K = D and negative for K > D.

## Failure scenario
1. On the pool deck someone notices that yaw turns lag and sets `ATC_DRAG_YAW` to a value estimated from a coast-down, "to cancel drag".
2. If the estimate is right, yaw is now undamped apart from the rate PID's D-term. Any overestimate makes the open-loop yaw axis unstable. The rate PID (P = 0.18, D = 0 on yaw by default) may or may not hold it, depending on thruster lag.
3. In the pool it shows up as a heading hold that overshoots and rings after every turn. The natural "fix" is more drag feedforward, which makes it worse.

## Suggested fix
- Move the drag term onto the **desired** rate: `yaw += K · des_rate · |des_rate|`, computed in `attitude_control.cpp` where the desired rate exists. Do the same for the cross-coupling terms (on the desired yaw rate).
- Add the missing linear damping term (`D_l · des_rate`), which matters more than the quadratic term at pool speeds.
- Refuse `XC_YAW2RLL` and `ATC_DRAG_RLL` on a frame where roll is unactuated (the 5-thruster tunnel hull, round-1 draft 00).
- Put the FF inside the PID's saturation test (round-1 draft 18, item 5).

## How to verify (bench)
- **Analysis / unit test:** simulate `I·ṙ = τ − D·r|r|` with the rate PID and K = 0, 0.5·D, 1.5·D. **Today:** at K = 1.5·D, an open-loop step (PID gains 0) diverges. **After** moving to the reference: the free response decays for every K ≥ 0.
- **Injection:** move the term back onto the gyro and confirm divergence returns.
- No water is needed to show the sign problem. The gain itself needs a coast-down in water.

## Severity: Medium
Latent (the defaults are 0), but it turns a tuning knob into a destabiliser, and the comment describing it tells the tuner the opposite.
