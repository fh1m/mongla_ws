# The Bar30 driver blocks the 500 Hz sensor task for about 4–6 ms per read, so the IMU is not polled and control runs on stale gyro

Part of the 2026-09-24 ecosystem review (tracking issue in fh1m/mongla_ws, link to follow).

## Summary
`MS5837::read()` starts the D1 conversion, then polls `delay(1)` until `millis()` has advanced by more than `wait`. It then does the same for D2. At the default OSR (`wait=1`) each wait takes 2 to 3 ticks, so a read takes about 4–6 ms plus the I2C transfers. It runs every 50 ms inside the 500 Hz sensor task, which also owns the BNO085 poll. For 2–3 control cycles in every 25, the IMU is not read and the control loop uses the previous gyro and attitude sample.

## Evidence
At commit `f1d3ba9`, `lib/MS5837/MS5837.cpp:130-139` (D1) and `:159-165` (D2):
```cpp
  uint32_t start = millis();
  while (millis() - start <= wait)
  {
    yield();
    delay(1);
  }
  uint32_t _D1 = readADC();
```
It is called from `src/drivers/bar30.cpp:144` (`s_ms.read()`), inside `task_sensor_read.cpp:69-72`. That is the same task, and the same loop iteration, as `bno085::poll(imu)` at `:62`. The sensor task is priority 6 on core 1 (`config.h:352-353`).

`bar30.cpp:139-143` notes that a higher OSR "made the read FAIL outright". This blocking, `millis()`-granular wait is a plausible contributor to that.

## Failure scenario
1. Every 50 ms the sensor task blocks for about 5 ms in `MS5837::read()`. `delay()` yields, so the control task (priority 5) keeps running at 500 Hz, but on a gyro sample 2–3 cycles old.
2. The rate loop's D term (filtered at 20 Hz) sees the gyro repeat and then jump, a small 20 Hz disturbance on all three rate loops.
3. Depth resolution is stuck at OSR 256, about 2 mm with jittery conversion timing. Raising OSR, which is the natural fix for baro noise in the depth D-term, cannot be done with a blocking driver, because OSR 8192 would block for about 40 ms per read.

## Suggested fix
Use a non-blocking state machine, called every sensor-task tick:
```cpp
enum { IDLE, D1_WAIT, D2_WAIT } st;  uint32_t t0_us;
switch (st) {
  case IDLE:    cmd(CONVERT_D1 + osr*2); t0_us = micros(); st = D1_WAIT; break;
  case D1_WAIT: if (micros() - t0_us >= conv_us[osr]) { D1 = readADC(); cmd(CONVERT_D2 + osr*2); t0_us = micros(); st = D2_WAIT; } break;
  case D2_WAIT: if (micros() - t0_us >= conv_us[osr]) { D2 = readADC(); compute(); st = IDLE; return NEW_SAMPLE; } break;
}
```
Use datasheet maximum conversion times in µs: 0.6 / 1.17 / 2.28 / 4.54 / 9.04 / 18.08 ms for OSR 256–8192. Each tick then costs one short I2C transaction. With the sample timestamped, this also enables the real-Δt depth rate in the depth D-term issue, and OSR 1024–4096 at 20–50 Hz.

## How to verify
- **Measure:** toggle a GPIO around `bar30::read()` and look at it on a scope. Today it is about 4–6 ms every 50 ms. After the change, no call should exceed 0.3 ms.
- Log the time between consecutive IMU updates (`imu_stamp_ms`) and plot a histogram: the gaps of 4 ms or more must disappear.
- Check that depth noise (standard deviation at rest) improves when OSR is raised.
- **Injection test:** add `delay(5)` in `D1_WAIT` and confirm the IMU gap histogram shows it again.

## Severity: Medium
It adds stale-gyro cycles to every rate loop and blocks the baro-noise fix. It is not a direct hazard.
