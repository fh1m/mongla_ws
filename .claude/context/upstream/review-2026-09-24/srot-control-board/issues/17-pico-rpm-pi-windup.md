# Pico RPM PI loop: the integrator winds up against the output clamp, slew and spin floor, integrates on telemetry up to 500 ms old, and the config values are not range-checked

Part of the 2026-09-24 ecosystem review (tracking issue in fh1m/mongla_ws, link to follow).

## Summary
In closed-loop RPM mode (`RPM_LOOP=1`), the Pico's PI integrator is clamped to ±1 **on its own**. The level it contributes to is then clamped, slew-limited and pushed to the spin floor, and none of that feeds back into the integrator. It keeps integrating while the output is pinned. The "integrate only on a real measurement" gate also allows any telemetry up to `PRESENT_TIMEOUT_MS` = 500 ms old, so a stale RPM is integrated at the full loop rate. The gains, idle, filter and slew in the config frame are accepted without range checks. The ESP32 forwards whatever `params::set()` accepted, and that is not range-checked either.

                float lvl = g_rpm_ff_a * (float)target;
                if (g_rpm_loop) {
                    float err = ((float)target - s_filt_rpm[i]) / g_rpm_max;
                    if (has_tlm) {                                            // integrate only on a real measurement
                        s_integ[i] += g_rpm_ki * err;
                        if (s_integ[i] >  1.0f) s_integ[i] =  1.0f;
                        if (s_integ[i] < -1.0f) s_integ[i] = -1.0f;
                    }
                    lvl += g_rpm_kp * err + s_integ[i];
                }
                lvl = constrain(lvl, -1.0f, 1.0f);

## Failure scenario
1. `RPM_LOOP=1`. Flasher issue #2 shows operators are told to set it. A thruster is asked for 3500 rpm, but the pack is sagging, so it saturates at `lvl = 1` doing 3000 rpm.
2. `s_integ` climbs to +1 even though the output cannot increase any further.
3. The demand drops to 1000 rpm. The integrator now has to unwind from +1 at `ki*err` per tick. For 100 ms or more the thruster stays near full throttle. That is overshoot on the one actuator the attitude loop assumes is fast.
4. A thruster's telemetry drops out, from a bidirectional DShot decode glitch or a disconnected ESC. For up to 500 ms, `s_filt_rpm` holds its last value, and the integrator winds towards ±1 on a measurement that is no longer changing.
5. Someone sets `RPM_KI=5` or `RPM_SLEW=-1` by mistake. Both are accepted, and the second disables slew limiting.

## Suggested fix
- **Conditional integration,** matching `pid.h`: compute `lvl_unsat` first, and integrate only if `|lvl_final| < 1` or `sign(err) != sign(lvl_unsat)`. A cheaper alternative is back-calculation: `s_integ += ki*err + kb*(lvl_final - lvl_unsat)`.
- **Integrate only on a fresh sample:** keep a per-thruster "new telemetry since the last tick" flag, set in the telemetry decode and cleared after use, instead of the 500 ms presence window.
- **Config bounds:** reject any non-finite value, and clamp `kp ∈ [0,5]`, `ki ∈ [0,1]`, `ff_a ∈ [0,1e-3]`, `slew ∈ [0,1]`, `filt ∈ [0,1]`, `idle ∈ [0,1500]`. Echo the values back in telemetry, or at least count rejections. Apply the same bounds on the ESP32 side (the params bounds table is covered in the FRAME_REVERSE / defaults issue).

## How to verify
- **Bench, one T200 in a bucket:** command 4000 rpm (unreachable) for 2 s, then 1000 rpm. Log the Pico `lvl` and the RPM. Today the fall to 1000 takes several hundred ms. After the fix it follows the feedforward within a few ticks.
- Pull the telemetry wire on one ESC for 300 ms and check that `s_integ` stays unchanged.
- **Injection test:** remove the saturation condition and confirm the overshoot returns.

## Severity: Medium
It only affects `RPM_LOOP=1`, which is off by default but documented as the recommended setting. In that mode, windup puts a delay on every thruster.
