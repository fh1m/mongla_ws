# MANUAL_CONTROL from two senders is merged: one global button-edge state, and no sender or target filter (a second station can toggle arm)

Part of the 2026-09-24 ecosystem review (tracking issue in fh1m/mongla_ws, link to follow).

## Summary
`onManualControl()` accepts every `MANUAL_CONTROL` frame regardless of `target`, sysid or compid. It computes button press edges against one global `s_prev_buttons`. When two stations send, for example Bondor over LoRa and the companion over USB, their frames interleave in two ways:
- The sticks jump between the two senders' values.
- Every alternation between a frame with a button held and one without produces a fresh "press". With `JS_ARM_TOGGLE` mapped, that toggles arm.

## Evidence
At commit `f1d3ba9`, `src/comms/mav_commands.cpp:691-734`:
```cpp
static uint16_t s_prev_buttons = 0;

static void onManualControl(const mavlink_message_t& msg) {
    mavlink_manual_control_t mc;
    mavlink_msg_manual_control_decode(&msg, &mc);
    ...
    uint16_t pressed = mc.buttons & ~s_prev_buttons;
    for (int i = 0; i < 16; ++i) {
        if (pressed & (1 << i)) { int func = (int)g_params.btn_func[i]; if (func != JS_NONE) runButtonFunction(func); }
    }
    s_prev_buttons = mc.buttons;
```
`mc.target` is never compared with `MAV_SYSTEM_ID`, and `msg.sysid` and `msg.compid` are never checked. Contrast `COMMAND_LONG` and `PARAM_SET`, which at least check `target_system` (`:597`, `:618`). The heartbeat handler already has a "configured companion" concept (`companionConfigured()` and `matchesCompanion()`, `:753`), but manual control does not use it.

## Failure scenario
1. The companion streams `MANUAL_CONTROL` at 20 Hz with `buttons=0`, because it drives `vision_align` or `vision_move` through STABILIZE. Bondor is also connected with a gamepad, and the pilot is holding a button mapped to `JS_ARM_TOGGLE` (or lights, gain, or mode).
2. The frames arrive as B(1), C(0), B(1), C(0) and so on. Every Bondor frame is a fresh rising edge, so `runButtonFunction` fires at the Bondor frame rate. Arm toggles on and off, and gain steps repeatedly.
3. Even with no buttons, `sp_forward` and `sp_yaw` alternate between the companion's command and the pilot's centred sticks. The vehicle sees a 50 % duty-cycle command and roughly half the authority the vision loop asked for.

## Suggested fix
- Accept `MANUAL_CONTROL` only when `mc.target == MAV_SYSTEM_ID` (or 0), **and** the sender matches a configured pilot: new params `JS_SYSID` and `JS_COMPID`, with 0 meaning "first sender to arrive owns the stick until 1 s of silence". A second sender's frames are dropped, with a rate-limited `STATUSTEXT "MANUAL_CONTROL from <sys>/<comp> ignored"`.
- Keep the button-edge state per sender, so that a handover does not create an edge.
- Button functions that change arm or mode go through `canArm()`. See #6.

## How to verify
- **Bench, props off:** send `MANUAL_CONTROL` from two pymavlink sources with different sysids at 20 Hz. Source A holds bit 0 (mapped to `JS_ARM_TOGGLE`) and source B sends 0. Today HEARTBEAT shows arm flapping. After the fix nothing flaps and A or B is rejected with one STATUSTEXT.
- **Injection test:** remove the sender filter and confirm the test above reproduces the flapping.

## Severity: Medium
A second station can toggle arm or halve the companion's authority. It needs two senders at once, which is the normal pool setup with Bondor plus the Pi.
