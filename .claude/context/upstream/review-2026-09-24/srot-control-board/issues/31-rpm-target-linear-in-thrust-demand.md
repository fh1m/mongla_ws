# RPM mode and the thrust trim treat a thrust-linear demand as RPM-linear: the target should be proportional to √|demand|, so the small-signal gain collapses near zero

Part of the 2026-09-24 ecosystem review, round 2 (see ../README.md).

## Summary
The mixer output `norm` is **thrust-linear**. That is the premise of `thstExpo()`, which inverts thrust ≈ (1−e)·thr + e·thr² on the raw-DShot path. In RPM mode (`RPM_LOOP=1`), though, the ESP32 sends `target_rpm = norm · RPM_MAX`, and the slow thrust trim (`THR_TRIM_EN`) predicts `rpm = RPM_MAX · |norm|`. For a propeller, T ∝ n², so the right mapping is **n ∝ √|norm|**. With the linear mapping:
- thrust goes as `norm²`, so the thrust gain at small demands collapses (at 10 % demand the vehicle gets 1 % thrust). Together with the 30 rpm `RPM_MIN_TGT` floor, this makes a large low-end dead zone.
- the thrust trim compares measured RPM against the wrong prediction. At part throttle it pushes every gain against its ±25 % clamp (`THR_TRIM_MAX`).

`config.h:208-224` attributes the "spin-up / stop" oscillation seen in RPM mode to RPM control *as an architecture*. That may be true. But part of it may be this mapping: the loop gain near zero is far below what the attitude loop was tuned for, so the attitude loop drives the thrusters in and out of the dead zone. *This is a hypothesis from the round-2 control review; it has not been tested.*

## Failure scenario
1. `RPM_LOOP=1` (flasher issue #2 says operators are told to set it). The heading-hold loop asks for a 5 % yaw correction.
2. The Pico is sent 5 % of RPM_MAX (about 180 rpm on a T200). That gives about 0.25 % of full thrust. The yaw error grows, the I-term winds up, the demand jumps into the region where thrust suddenly appears, the vehicle overshoots, and the cycle repeats. This matches the "spin-up / stop / spin-up" description.
3. With `THR_TRIM_EN=1` on raw DShot, at 30 % demand the trim predicts 30 % RPM. With expo 0.65 the thruster actually spins faster than that, so the trim concludes the thruster is "strong", reduces its gain, and pins at −25 %.

## Suggested fix
- RPM target: `rpm_tgt = sign(n) · RPM_MAX · √|n|`. Optionally apply a reverse-direction factor (the T200 reverse thrust is about 23 % weaker for the same |n|; the host already uses 0.77) as `rpm_tgt_rev = … · √(|n|/k_rev)`.
- Thrust trim: `pred = RPM_MAX · √|d|` (or the inverse of whatever thrust model the raw path uses, so both paths share one model).
- Then **re-run the RPM-loop trial** against open loop on bucket steps (0→50 % and 50→0 %). If the RPM loop settles faster with under 10 % overshoot, this mapping was a cause of the oscillation. If it does not, `config.h`'s architecture explanation stands and RPM mode stays off. Either result is worth having.
- Keep one thrust model for both the raw and RPM paths, and have a test compare them. Today they disagree.

## How to verify (bench)
- **Unit test:** for n ∈ {0.05, 0.1, 0.25, 0.5, 1.0}, the target must be `RPM_MAX·√n`. Thrust (∝ target²) must then be linear in n.
- **Bucket, one T200, `RPM_LOOP=1`:** command n = 0.1 and n = 0.4 and measure thrust (load cell) or RPM. **Today:** thrust ratio ≈ 16:1. **After:** ≈ 4:1.
- **Injection:** revert to linear and confirm the unit test fails.

## Severity: Medium
Both affected paths (RPM mode and the thrust trim) are off by default. On either one the error is a √ in the plant gain, and it may be the actual reason RPM control was abandoned.
