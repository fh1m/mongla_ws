# Proposal: move the IMU off the shared I2C0 bus (BNO085 over SPI, or an ICM-42688-P over SPI with on-board attitude fusion)

Part of the 2026-09-24 ecosystem review (tracking issue in fh1m/mongla_ws, link to follow).

## Summary
The BNO085 and the Bar30 share I2C0 at 400 kHz, serviced from the core-1 sensor task. The BNO's SHTP over I2C uses clock stretching and has caused repeated trouble:
- the reset storms of 2026-07-24
- the INT-gated polling workaround, needed because the Adafruit I2C API ignores INT
- the 3-report limit (`LINEAR_ACCELERATION` was dropped)
- a heal path that blocks the task (a separate issue)
- a pressure excursion caused by a report reconfiguration colliding with a Bar30 conversion (`bar30.cpp:139-143`)

Moving the IMU to its own SPI bus removes that whole class of problems and frees I2C0 for the baro.

## Evidence
At commit `f1d3ba9`.
- `include/config.h:79-86`: `PIN_I2C0_SDA 21 // BNO085 IMU + Bar30 depth`, `I2C0_FREQ 400000`.
- `ROADMAP.md`, 2026-07-24 entries: "the BNO085 was resetting repeatedly (OLED r8) ... chained resets = a multi-second frozen angle". Also: "if rN climbs again, drop back to 200 kHz".
- `src/drivers/bno085.cpp:89` records that the extra reports were dropped. `bar30.cpp:139-143` records the bus collision between the mag report and a baro conversion.

## Proposal
Two options, in order of effort:

**A. Same part, SPI (lowest risk).** The BNO085 supports SPI up to 3 MHz, with INT and a wake pin, and `Adafruit_BNO08x::begin_SPI(cs, int, …)` uses INT natively. The cost is 4–5 GPIOs and a board spin, with the same fusion and the same calibration flow. Benefits:
- no clock stretching
- more reports within the budget (linear acceleration returns for the vertical estimator)
- no shared-bus stalls with the Bar30

**B. A raw IMU with our own fusion.** An ICM-42688-P (about $5–15 per part; also used in ArduPilot and PX4 flight controllers) over SPI at 1–2 kHz ODR, with FIFO and data-ready interrupt. Run a small complementary or Mahony filter on core 1 (tens of µs at 500 Hz) with an **explicit gyro-bias state** that we own. That fixes the double-bias ambiguity in the hygiene issue. It gives deterministic latency and full-rate accelerometer data for the vertical estimator, and removes the SHTP black box. The cost is the fusion code, tests, and the loss of the BNO's magnetometer fusion (a separate magnetometer would be needed if absolute yaw is still wanted; today `MAG_YAW_REF` is a one-shot).

Either way, I2C0 then carries only the Bar30, and the self-heal problem goes away.

## How to verify (before committing to a board spin)
- **Measure the current cost:** log `bno_reset_count`, `s_reinit_count` and the IMU inter-sample gap histogram over a 1 h bench soak with thrusters spinning (EMI) at 400 kHz. That sets the baseline.
- **Prototype A** on a breakout with jumpers to spare pins. Repeat the soak. The gap must be ≤ one report period (2.5 ms) at p99.9, with zero resets.
- For B, run the fusion on recorded raw data against the BNO's quaternion, then do a bench tilt test with a known angle (a machinist's square).
